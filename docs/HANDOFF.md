# Handoff and export

The scenario this exists for: someone on shift has narrowed an incident to a
window and a set of records, and now has to hand it to another team — L3 support,
a vendor, a supplier's on-call — who has none of the context and cannot see the
original machine.

Most log tools stop at "you can copy the rows." That is the wrong artefact. What
the receiving engineer needs is enough to **reproduce and trust** the finding
without a conversation, because the person who found it is going back to fixing
the outage.

This is a small feature. It is also the one that decides whether the tool gets
used in an actual incident or only at a desk.

---

## 1. Command

```bash
loupe ./logs '02:00-07:30 level:>=error' --handoff cds-incident.md
loupe ./logs '02:00-07:30 level:>=error' --handoff - | pbcopy
loupe ./logs '02:00-07:30 level:>=error' --handoff bundle.zip --include-raw
```

Formats by extension: `.md` (default, pasteable into a ticket), `.json`
(machine-readable), `.zip` (bundle with the raw source excerpts).

---

## 2. What a handoff must contain

Ordered by what the receiver reads first.

1. **The window in both timezones**, plus the date, plus which zone the query was
   written in. `02:00–07:30 BST = 01:00–06:30 UTC, Wed 2026-08-13`.
2. **The exact query string**, so it can be re-run verbatim.
3. **The source files**, with sizes, formats, record counts, and — critically —
   whether each file's timezone was **known or assumed**. A receiver who does not
   know an assumption was made cannot check it.
4. **Counts**: records matched, records excluded for having no timestamp, records
   the parser rejected. Silence about excluded data is how handoffs mislead.
5. **The records themselves**, in the display timezone, with a UTC column.
6. **The raw lines**, verbatim, in their native format. The receiver may not trust
   your parser, and they are right not to. Always include them.
7. **Provenance**: tool version, hostname, who ran it, when.

## 3. Markdown output shape

```markdown
# Log extract — checkout-api CDS failure

**Window**   02:00–07:30 Europe/London (BST, UTC+01:00)
             01:00–06:30 UTC · Wed 2026-08-13
**Query**    `02:00-07:30 level:>=error`
**Matched**  412 records across 4 sources
**Excluded** 18 records had no parseable timestamp (see appendix)

## Sources

| File | Format | Records | Timezone |
|---|---|---|---|
| checkout-api.log | jsonl | 2,104 | known (RFC3339, UTC) |
| postgresql.log | postgres | 880 | **assumed UTC** — no offset in format |
| access.log | nginx-combined | 6,022 | known (+0000) |
| payment-worker.log | log4j | 431 | **assumed UTC** — no offset in format |

## Records

| Time (BST) | Time (UTC) | Level | Source | Message |
|---|---|---|---|---|
| 02:14:06.221 | 01:14:06.221 | ERROR | postgres | FATAL: remaining connection slots… |
…

## Raw lines
```
2026-08-13 01:14:06.221 UTC [20044] ERROR: remaining connection slots are reserved…
```

---
Generated by loupe v0.4.1 on host-01 at 2026-08-13T08:02:11Z
```

Cap the record table at 200 rows by default with `--limit`, and always state when
output was truncated and what the full count was. A truncated extract that does
not say it is truncated is worse than no extract.

## 4. Design rules

- **The handoff is generated from the same query path as the display.** It must
  never be possible for the exported records to differ from what was on screen.
  Same AST, same SQL, different renderer.
- **Assumptions are surfaced, never hidden.** Assumed timezones, truncation,
  excluded records, and unparsed lines all appear in the output whether or not
  they are interesting.
- **Raw lines are always included.** No flag to omit them by default.
- **No network, no upload, no share links.** This writes a file. That is the whole
  feature, and it is why it can be trusted with production logs.
- **Redaction is opt-in and explicit:** `--redact user_id,email` replaces values
  with a stable hash so records can still be correlated without exposing the
  value. Never redact by default — silently altering evidence is worse than
  exposing it, and the operator knows their disclosure rules better than the tool
  does.

---

## 5. Why this is worth building early

It is roughly a day of work, it has no dependencies beyond the query layer, and it
is the difference between "nice local tool" and "thing our on-call rota uses."

It is also unusually good README material: a screenshot of a generated handoff
communicates the tool's purpose faster than any description of its query syntax.

Schedule it in M4, after the UI, before launch.
