# Benchmarking loupe

How to measure this tool so that the number at the end means something.

It is written from a post-mortem of one real attempt: a 26-minute session on
2026-08-26 against a 250,000-line, 48 MB, 15-format merged corpus, which
produced twelve genuine bug reports and a usability score that turned out not to
measure usability. That run's artefacts — the corpus, its generator
`gen_logs.py`, the operator's `bugs.md` and `solution.md`, and the captured
transcripts — are not in this repository; they are working material kept
alongside it. Everything this document needs from them is quoted inline, so it
stands on its own.

The prescription is in [What a true test looks like](#what-a-true-test-looks-like).
The post-mortem below is there because each rule exists to prevent a specific
thing that actually went wrong.

---

## Verdict on that run

**It was a good bug hunt and not a usability benchmark.** Every finding it
produced was real, reproducible, and worth the time it took — five of them were
invariant violations. But the thing it set out to measure, "whether loupe is
usable at 4am", was not what got measured.

What got measured was **parser coverage**. 67 % of the corpus carried no
timestamp because four parsers were missing or broken, so 16 of 24 tasks were
answered with `loupe sql` plus a hand-written regex over `raw`. That is DuckDB
doing grep's job inside loupe's process. The resulting 32/48 is a proxy for "how
many formats does loupe parse", which is one *input* to usability, not usability.

The distinction matters because the two have different fixes. Poor coverage is
fixed by writing parsers. Poor usability is fixed by changing the interface. The
run could not tell them apart, so it could not say whether loupe's interface is
any good — and after the parser work, it turns out it mostly is: 20 of the 24
tasks now answer from the filter DSL directly.

---

## Six reasons it was not a true test

### 1. A blocked precondition was scored as a result

You cannot measure whether `status:>=500` is a good way to ask a question on a
corpus where `status` does not exist. Tasks 4, 5, 9, 21, 22 and 24 were scored
as usability failures when they were coverage failures that happened to be
observed through the usability interface.

**Parser coverage is a gate, not a scored dimension.** A run that begins below
the gate is measuring the gate.

### 2. The ground truth is wrong

`answer-key.json` is generated by `gen_logs.py` from its own internal counters.
Regenerating it (`--lines 250000 --seed 20260821`) reproduces the corpus
byte-identically, so the corpus is sound — but four of the key's seven exact
counts disagree with the file the generator itself wrote:

| Metric | Answer key | Actual (`awk`, and loupe) |
|---|---|---|
| HTTP 5xx | 7,339 | **7,340** |
| HTTP 502 | 3,582 | **3,583** |
| Postgres `FATAL:` | 1,824 | **1,825** |
| Distinct nginx client IPs | 34,093 | **34,094** |
| App JSON ERROR or FATAL | 4,809 | **4,811** |
| `Failed password` lines | 2,611 | 2,611 ✓ |
| …of those, for `root` | 243 | see §3 below |

The generator emits some lines without incrementing the counter for them. Every
count is short, never long, and consistently by one — except the JSON errors,
short by two.

The consequence is worse than an inaccurate score. The benchmark's own text says
exactness "is a proxy for whether loupe's filters are line-accurate or
sampling", and then grants partial credit within 2 %. So a tool that returned the
**correct** answer was marked "approximately right", and the one property the
tier exists to test was never actually tested.

*(A caution found while checking this: on this corpus `ugrep 7.8.4`, installed
as `grep` on the test machine, returns 2,563 for a pattern where `awk` and loupe
both return 2,564, and matches the missing line when handed it alone. Whatever
derives the ground truth must not be a tool whose behaviour on hostile input is
part of what the corpus is designed to stress.)*

### 3. At least one task's stated answer does not match its stated question

Task 8 asks for `Failed password` lines "for `root`" and answers 243. The corpus
contains 140 `Failed password for root` and 103 `Failed password for invalid
user root`. Both readings are defensible; the task does not say which it wants,
so a literally correct answer scores zero. A task whose wording admits two
answers is measuring the reader, not the tool.

### 4. The evidence chain is broken as shipped

- `answer-key.json`, described by the benchmark as its machine-readable ground
  truth, is **not in the folder**.
- The `screenshots/` directory is **not in the folder**, though the bug report
  embeds 18 images from it and the worked solution points readers at it.
- Two transcripts in the evidence set are not results: one is a run against an
  unrelated directory, the other a run of a binary with no web UI compiled in.
  Both are filed alongside the real ones without a marker saying they are not.
- The runner script hard-codes an absolute path outside the folder, and a
  `LOUPE/` sibling directory that is not in it.

A benchmark nobody else can re-run is a report, not a benchmark.

### 5. Tier 5 was never run — and it is where the real problem was

The 5M-line (~960 MB) and live-follow tiers were skipped. They are the tiers
that test the performance claims, and the performance claims are the weakest
thing in the project. Measured properly:

| | Measured | `CLAUDE.md` target |
|---|---|---|
| 323 MB of single-format JSON lines, cold | **63 s** (5.1 MB/s) | 1 GB in 20 s (51 MB/s) |
| 48 MB merged, 12 formats, cold | 16 s | — |
| Cached re-open | 0.35 s | under 200 ms |

The documented target is out by roughly **10×**, and per-line detection is not
the cause: the single-format path uses one parser and is still parse-bound. The
run's finding #11 attributed the slowness to the mixed dispatcher and suggested
a detection cache. The cache was worth building and it helped the merged case,
but it does not touch the number that is actually wrong. Tier 5 would have found
that in one command.

### 6. "0 fallbacks to grep" is not what the run showed

The worked solution's summary table reports **0** fallbacks. Its scoring section then
correctly scores 16 tasks as fallbacks, because
`loupe sql "… regexp_matches(raw, '^[0-9.]+ \S+ - - \[') …"` is grep with extra
steps. The scoring is right and the headline contradicts it. The headline is
what gets quoted.

## What a true test looks like

### 0. Gate first, then score

Run this before anything else, and stop if it fails:

```bash
loupe sources <corpus>
```

**Gate:** every format the corpus contains appears as a row, and
`NO TIMESTAMP` is zero except for formats that genuinely carry no clock (CI
runner output carries elapsed time, not a wall clock, and never can).

Below the gate you are benchmarking the parser set. Fix that first, publish the
coverage table as its own result, and only then run the usability tasks. The two
numbers answer different questions and averaging them answers neither.

### 1. Three corpora, not one

`platform-mixed.log` is excellent and insufficient by itself.

1. **The synthetic corpus** (`gen_logs.py`). Deterministic, hostile, with a known
   story. Keep it. It is the only one where exact ground truth is possible.
2. **Real logs.** A few hundred MB of genuine nginx, journald, Postgres and
   Kubernetes output, redacted. A parser tuned against `gen_logs.py` scores well
   on `gen_logs.py`. Real nginx has `log_format` variants nobody invents.
3. **One format at volume.** 1 GB of plain JSON lines, so the documented
   throughput claim is tested against the case it describes rather than against
   a 15-format merge that was never in scope for it.

The synthetic corpus should also be regenerated at a **fresh seed** for the
scored run. A benchmark whose needles sit at line 17,969 every time is one
`grep -n` away from being memorised, and the tool's author has read it.

### 2. Ground truth derived twice, by different means

Every exact count must be produced two ways that share no code:

1. the generator's own counters, and
2. an independent pass over the emitted file (`awk`, or a short script).

**They must agree, and the run fails if they do not.** Both numbers go in the
key. This one rule would have caught all four errors in §2 above, and it is the
same principle the tool under test is built on: a single source of truth that
cannot be cross-checked is an assumption, not a fact.

### 3. Tasks written as intents, with the acceptance criterion separate

Each task gets three fields:

- **Intent** — what the operator wants, in their words. *"How many requests did
  the edge fail outright?"*
- **Acceptance** — the exact value, and what counts as correct, stated
  unambiguously. *"7,340 — nginx `status` 5xx plus haproxy `status` 5xx; does
  not include upstream 5xx logged by nginx error."*
- **Designed path** — the one command the tool's author believes should answer
  it. *`loupe <dir> 'status:>=500 stats count()'`*

The designed path is the point. Recording it in advance turns "did it work" into
"did the tool's intended answer work, and if not what did the operator do
instead", which is the usability signal the current scoring is reaching for and
cannot quite express.

### 4. Measure the interaction, not only the answer

Per task, record:

| Field | Why |
|---|---|
| Wall-clock time from reading the task to having the answer | The 4am number |
| Commands issued, verbatim | The only honest record of what happened |
| Whether the designed path was used | Did the feature meant for this work |
| Whether `loupe sql` was used | Escape hatch, count it as an escape hatch |
| Whether anything outside loupe was used | grep, awk, an editor, `less` |
| Number of failed or corrected attempts before the working one | Discoverability |
| Whether the operator had to read the docs | Discoverability |

Failed attempts are the field the current run is missing entirely, and the one
that best predicts whether someone will still be using the tool next month.

### 5. Scoring that separates the two axes

Score each task on both, and never combine them:

- **Capability** — 1 if the correct answer was obtained by any means, else 0.
- **Ergonomics** — 3 designed path, first try · 2 designed path after a
  correction · 1 escape hatch (`loupe sql`) · 0 left the tool.

A tool that scores 24/24 capability and 30/72 ergonomics has a usability
problem. A tool that scores 16/24 capability has a coverage problem. One number
cannot say which, which is exactly what happened to the 32/48.

### 6. Blind, and run twice

- The operator running the tasks must not have written the corpus, the key, or
  the tool.
- The scorer must not be the operator.
- Run the whole suite twice with different seeds. A tool whose answers move
  between seeds has a nondeterminism bug; a benchmark whose *scores* move a lot
  between seeds is measuring luck.

### 7. A baseline to compare against

"26 minutes for 24 tasks" means nothing on its own. Run the same task list with:

- **`grep`/`awk`/`less` only** — the honest floor, and the thing loupe must beat.
- **`jq` plus `grep`** — what a competent engineer actually reaches for.
- Optionally the tool in the pitch: time to stand up a container, ingest, and
  answer task 19.

loupe's claim is "you do not need Elasticsearch for this". That claim is
untested until someone measures both.

### 8. Tier 5 is not optional

It is the tier that tests the numbers most likely to be wrong.

```bash
python3 gen_logs.py --lines 5000000 --seed <fresh> --out big.log --key big-key.json
loupe sources ./big                       # time to first output, peak RSS
loupe ./big 'status:>=500 stats count()'  # cold, then cached
loupe ./big '"<a tier-3 needle>"'         # filter latency on 5M rows
loupe ./big --follow                      # append 200k lines, watch it keep up
```

Record time-to-first-render, peak RSS, cold and cached ingest, and per-filter
latency. Assert against `CLAUDE.md`'s stated targets **by name**, so that a
target the code cannot meet is either fixed or corrected rather than quietly
carried.

### 9. Reproducible by someone else, from the folder

The folder must contain, or generate on demand:

- `gen_logs.py`, the seed, and the exact command line used.
- `answer-key.json`, **both** derivations, and the cross-check script.
- The loupe commit, and the exact build command.
- Every transcript, with any run against the wrong corpus or a stale binary
  either deleted or clearly labelled as such.
- Screenshots, if the report embeds them.

Nothing should hard-code a path outside the folder. The 2026-08-26 runner did.

## What to expect if it is re-run now

The parser and DSL work done in response to that run changed the shape of the
result. On the same corpus, byte-identical:

| | Before | After |
|---|---|---|
| Formats recognised | 6 | 12 |
| Records with no timestamp | 148,202 (67 %) | 1,718 (0.8 %) — all CI output, which has no clock |
| Records no parser claimed | 76,932 | 1 |
| Tasks needing `loupe sql` | 16 of 24 | 4 of 24 |

The four remaining are worth stating plainly, because they are the honest
starting point for the next run rather than something the fixes hid:

1. **Task 9** (distinct client IPs) — the DSL has no `count_distinct()`
   aggregate. `loupe top client <dir> 'format:nginx'` reports the distinct count
   in its footer, so the answer is reachable, but not the way the task asks.
2. **Task 22** (prove the file is not sorted) — needs a window function.
   Reasonable to leave in `loupe sql`.
3. **Task 12** (longest line) — needs `length(raw)`. Same.
4. **Task 24** (reconcile a `Z` log with a `+10:00` log 90 s apart) — works, but
   only because `--source-tz` is passed. That flag names a *source*, and one
   merged file is a single source carrying a dozen formats, so it cannot say
   "the Postgres lines are AEST, the app JSON is UTC". Per-format zone
   assignment does not exist.

A true test should keep all four visible rather than scoring around them.
